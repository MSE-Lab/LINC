## 关键设计决策

### 1. 为什么延迟补边?

**增量阶段的核心任务是:**

```
决定: 新序列属于哪个簇?是否新增为代表?

答案: 仅需知道"新序列与代表的关系"
      不需要知道"新序列与簇内所有普通成员的关系"

原因: 代表的本质是簇的概括
      与代表的关系足以判定归属
```

**增量阶段如果实时补边会怎样?**

```
问题: 当簇规模增长到 1000+ 成员时

新序列 X 进入:
  - 需要与所有 1000 个成员逐一比对
  - 复杂度 O(1000) → 重新逼近 O(N²)

延迟补边的优势:
  - 增量阶段只比代表 O(reps)
  - 补边阶段只做一次 O(all_pairs)
  - 两者互不干扰,效率最优
```

### 2. 数学等价性保证

**LINC 的补边不是近似,而是严格完备:**

```
全量计算 (黄金标准):
  1. 所有基因两两比对
  2. 所有边同时建立
  3. 边集合 = {所有可能的边}

LINC 计算:
  阶段1-3 (增量): 部分边已建立
  阶段5 (补边): 补全剩余边

数学保证:
  - 补边阶段补全所有"增量阶段跳过的边"
  - 补边阶段不重复"增量阶段已计算的边"
  - compared_pairs 精确记录每个已比对的对

结论: 边集合 ≡ 全量计算的结果
```

### 3. 计算剪枝策略

#### 长度预过滤

```python
def length_filter(seq1, seq2, threshold=10.0):
    """
    生物学观察: 两条长度差异过大的序列
                不可能满足覆盖度阈值
    """
    ratio = max(len1, len2) / min(len1, len2)
    return ratio > threshold
```

#### 已比对去重

```python
def should_compare(pair, compared_pairs):
    """
    确保每个基因对最多被比对一次
    """
    sorted_pair = tuple(sorted(pair))
    return sorted_pair not in compared_pairs
```

**剪枝效果:**

```
剪枝前:
  10000 个基因 → 49,995,000 基因对

剪枝后 (假设 45% 压缩率 + 30% 长度过滤):
  有效比对: 约 17,000,000 对
  减少: 66%
```

### 4. 并行化策略

```python
# 各簇独立处理,天然可并行
with ThreadPoolExecutor(max_workers=n_cpus) as executor:
    futures = {
        executor.submit(complete_cluster_edges, cluster): cluster
        for cluster in clusters
    }
```

- **无数据竞争**: 各簇的 `compared_pairs` 私有
- **无加锁**: 补边结果写入共享集合 (GIL 保护)
- **接近线性加速**: 可用核心数 = 加速比
